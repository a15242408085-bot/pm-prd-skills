# 从 PRD 到评测集

读取 PRD、真实坏案例与已有验收规则。保留 `REQ-ID`、`AC-ID`、`RISK-ID`，为用例分配 `CASE-ID`。用例来源不足时可创建明确标为 synthetic 的案例，不能冒充真实用户记录。

## 设计

1. 先确定评测目的：能力探索或回归保护。回归只包含已批准应满足的能力，探索失败不自动等于不能上线。
2. 每项核心验收覆盖正常与异常，适用时加相邻案例，防止过度拒答、误报或多余操作。严重失败编成 critical 用例。
3. 每个任务明确输入、初始环境、角色权限、fixture、期望行为、禁止结果、评分方式和实际证据。原始资料不足时说明依赖，不能只生成一段参考答案。
4. 可确定判断的条件交给代码检查；语义判断写 rubric 并用人工标注校准；高风险判断安排领域审阅。评分说明应让独立评审者有机会达成一致。
5. 记录模型、Prompt、工具和数据版本，规定每任务 Trial 次数及环境重置。参数与阈值待团队确认；只有 approved=true 的规则才能用于已批准的门槛判断。
6. 将真实 Outcome 纳入评分，尤其是状态修改和来源核查。成功声称与工具实际结果不一致时不能算通过。

## 输出格式

使用 [JSON 交接格式](references/eval-format.md)。该格式属于本技能包，不推定第三方 runner 能直接执行。若用户已指定其他 Harness，优先沿用其 schema 并保留映射；转换后不要调用本格式的结果汇总脚本。

输出评测集、验收覆盖与未覆盖项、真实／合成来源说明、评分器校准计划及未批准阈值。只设计用例时，状态写“未运行”。
